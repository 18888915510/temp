# fix1-2a：单独核对 Outlook 与邮件 CLI 的关系

目的：用户在 P1 点击跟进后遇到 Outlook 数据文件占用、窗口打不开。旧解释“CLI 让 Outlook 锁文件”只是推断；这轮先做对照取证，不启动 Hub、不调用模型，不把调用量收窄当成已修复。

授权来自 CODEX-P1-fix1.md 第 2a 步：只读查询、受控邮件读取、在本机新建诊断脚本及安全数字记录；不得改 Outlook、WeLink、Hub、用户设置、信任设置，不删除任何文件、不结束现有进程、不发消息、不调用邮件写命令。禁止自动修复、安装/升级、修改系统代理。遇到权限/登录/参数错误即停，先交已有证据。每个主动调查阶段最多 15 分钟，用户观察等待不计入，不反复开轮询任务。

## 0. 先确认用户在场

可以先定位 CLI、读帮助和相关本机文档；**任何 mail list/get 调用前**，在公司会话里请用户确认：“Outlook 现在能正常打开，已保持打开，可以开始对照。”未收到确认不得启动邮件读取。一次只向用户提出这一件事，不启动 2b。

原始报错截图和邮件内容仅在公司电脑看，不回传。旧 5～12 分钟试用报告不能用作本轮重复实验的结果。

## 1. 路径与准备

1. 在 `%USERPROFILE%\followup-eval` 只读确认已有文件状态，允许 `git pull --ff-only` 取得本任务。存在冲突或不明已跟踪改动即停，不清理以前的日志/结果。
2. 从 Hub 已有 `welink-ro.cmd` / 已配置的 CLI 路径找到实际使用的 `welink-cli.exe`，核对版本和 `mail --help`、`mail list --help`、`mail get --help`。读取相关本机文档，查调用是 HTTP/Exchange 还是 Outlook/MAPI；帮助没说就记未知，不猜。不得打印私有完整路径、账号、凭据或代理值。
3. 在 `%TEMP%` 新建唯一的 `AIHubFollowupFix1-<时间>` 诊断目录，绝不覆盖旧目录。可在这里创建 PowerShell 只读调用脚本，只保存命令种类、序号、时间、耗时、退出码、是否有效 JSON、条数等安全记录。邮件 CLI 的 stdout/stderr 只在内存解析，不写报告/日志，不启用 Transcript，不把邮件编号拼到输出里。现有原始文件不删除。
4. 记录当前 `Get-Process OUTLOOK* | Select Id, StartTime`。这是**现在仍在运行的进程**，不能据此宣称此前报错时谁占用了文件。若旧日志没有当时进程证据，历史占用者写未知。不主动打开 .ost，不修改邮件配置。

## 2. 路线取证（用户确认在场后）

执行一次 `mail list --folder-id inbox --max 3 --is-read 1 --offset 0`，用新建的 CLI 子进程 PID，在其运行期间采样：

- `Get-Process -Id <本次PID> | Select-Object -ExpandProperty Modules`：仅留下模块名称，重点 `olmapi32.dll`、`mapi32.dll`、`mso*.dll` 等。读不到、权限不足、命令太快没采到就记“未观测”，不能写“未加载”。若入口是 shim，确认实际子进程 PID，不能把另一个已有进程当本次 CLI。
- `Get-NetTCPConnection -OwningProcess <本次PID>`：仅记有无连接、数量、状态类别和采样时间，不回传地址、端口、主机名。**存在 TCP 连接不等于已证明是 Exchange，也不能排除进程内 MAPI**；只在本机文档和模块证据支持时解释路线。
- 记录命令开始/结束时间、退出码，核对脚本的内存输出解析结果，不回传正文或截断原文。

## 3. 旧量与新量各一次，禁止为结果重复运行

脚本串行调用原生 exe，不通过 Hub。不调用 `mail autodiscover` 或其他设置命令。用本机已存在的登录态；需要交互就停。取邮件只选本来已读的邮件（`--is-read 1`），因为未读邮件的副作用尚未确认；这是与原 P1 的 `--is-read -1` 的明确差异，必须写进结论，不能冒充逐字复现。

1. **旧调用量**：`mail list --folder-id inbox --max 100 --offset <0,100,...,900> --is-read 1` 共 10 页，连续串行、不另加间隔；从返回列表选择 30 封不同的已读邮件，以 `mail get --item-id <本机编号> --body-type Text` 各读一次。编号仅在内存使用，不报告。每条记录开始/结束时间、耗时、退出码、JSON 是否有效。若只有不足 30 封，实际读多少报多少，不拿同一封凑数；此时不声称完成原调用量。任何调用错误、用户报告 Outlook 错误立即停止后续调用，保留已经执行的计数，不自动重跑。
2. 本阶段结束后只问用户：“刚才 Outlook 是否报错，若有是几点？”将用户观察与命令时间线分开列出。若已打不开，先停在这里；不得由你杀进程、重开 Outlook 或修复文件。待用户自行恢复且明确说 Outlook 已正常后，才可进行新量对照。
3. **新调用量**：list 2 页（每页 100），get 最多 10 封不同已读邮件；每一条邮件命令结束后，下一条开始前至少等待 500 毫秒，所有邮件命令串行。优先采用旧实验读取过的相同邮件，便于比较；不够则如实记录。每条同样记时间和结果。这个实验验证调用强度，**不是**业务筛选的回放；业务新实现只收同会话/主题、10 次 get 含种子。
4. 结束后再次只问 Outlook 是否报错、几点；记录本阶段开始/结束时 Outlook 的 PID/StartTime，注明两阶段之间用户是否重开过 Outlook。两阶段条件变化必须列出。

## 4. 如何下结论

- 假设 A：CLI 直接调用 MAPI/Outlook。预期在本次进程模块/本机文档中有证据；加载 DLL 仅证明组件参与，不等于已锁 .ost。
- 假设 B：请求密集触发客户端冲突。预期旧量下出现用户所说错误，新量在可比条件下不出现；一次对照只能支持关联，不能证明普遍安全。
- 假设 C：Outlook 自身或其他程序占用。需要独立进程/句柄或可复现证据；本次都没报错不能证明与 CLI 无关。

分别回答：实际调用路线证据、旧量/新量完成数量及失败、用户观察、当前进程事实、未知项。对照未完成或双方均未复现时写“未能确定”，不得通过推断批准 2b。

**只有家里核对接受“旧量复现、新量不报错”，或独立证据证明“与 CLI 无关”后，才会另发 2b。不要自行运行另一份任务。**

## 5. 安全摘要交付

只在两阶段/用户观察完成后，或遇阻需要交接时，给一份明确标“验收摘要，不是原始日志”的报告。可在 `%USERPROFILE%\followup-eval\results\fix1-outlook-<时间>.md` 新增，核对内容安全后只 add 此文件、commit/push 到 temp main，核对 `git ls-remote origin refs/heads/main`；不提交原始目录、脚本运行数据、CLI 输出、截图或源码。可只回执不上传，但必须说明。

每份报告/回执最多 64,000 UTF-8 字节，回传前核对源文件精确字节数、mtime、SHA256。单文件达到 20,000,000 字节或大小未知不得回传；不能压缩、编码、分页、分片或多轮重建绕过；源端分析后只回安全统计。任何真实消息/邮件正文、人名、群名、邮箱、账号、URL、主机/IP、凭据、原始邮件编号都不得回传。模块只报文件名，目录用环境变量占位。列出跳过文件的占位路径、大小和原因。
